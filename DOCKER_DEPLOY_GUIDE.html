BenchVault v5.0.4

Deployment Guide

Operating an existing BenchVault deployment: configuration, HTTPS, backups, upgrades, and diagnosis.

Installing for the first time? Start with the Install Guide. This document assumes BenchVault is already running and you now need to run it well.

Looking for the in-app admin screens — users, roles, audit log, the Cloud Backup panel? Those live in the Administrator Guide. This guide covers only what you do from a terminal.

BenchVault ships as one Docker Compose stack: db (PostgreSQL 16), api (FastAPI, migrates on boot), and caddy (serves the React SPA and reverse-proxies /api). The same command runs it identically on a Linux VPS and on Windows Docker Desktop.

Configuration (.env)

.env is authoritative. The db and api containers read it directly via compose env_file, not via variable interpolation. Environment variables exported in your host shell — including legacy desktop-era POSTGRES_DB or POSTGRES_PASSWORD — therefore cannot override it. What you put in this file is exactly what the containers get.

The exception is values compose interpolates rather than passes through env_file: HTTP_PORT, HTTPS_PORT, DOMAIN, BENCHVAULT_COOKIE_SECURE, and BENCHVAULT_ENABLE_API_DOCS still follow normal shell precedence, so HTTP_PORT=8080 docker compose up -d works while POSTGRES_PASSWORD=x docker compose up -d silently does nothing.

Variable Purpose
POSTGRES_PASSWORD Required. Database password. Never typed by users.
POSTGRES_DB / POSTGRES_USER Database name and user. Set both explicitly — the postgres image defaults them to postgres, and the API needs a name.
DOMAIN Blank = LAN plain-HTTP on :80. A real domain = Caddy auto-HTTPS on :443.
BENCHVAULT_COOKIE_SECURE false for LAN HTTP, true for HTTPS. Must agree with DOMAIN or login breaks silently.
HTTP_PORT / HTTPS_PORT Host ports to publish. LAN use only — see TLS below.
BENCHVAULT_ENABLE_API_DOCS 0 hides the /docs API explorer. Consider it for public deployments.
JWT_SECRET_KEY, BenchVault_ENCRYPTION_KEY Optional. Auto-generated and persisted under /data/config if unset.
BENCHVAULT_UPDATE_CHECK_TOKEN Optional. Read token (fine-grained PAT) for the automatic update check when the repository is private; unset for public repos.
BENCHVAULT_AUTO_BACKUP_INTERVAL_HOURS Optional. How often the automatic cloud backup runs when enabled in the app's Cloud Backup panel (default 24).

After changing POSTGRES_*, the db container needs docker compose down then up -d — a plain up -d will not apply them.

LAN versus public HTTPS

LAN / plain HTTP

DOMAIN=
BENCHVAULT_COOKIE_SECURE=false

Caddy serves HTTP on port 80. Reachable at http://<host-ip>. Remap with HTTP_PORT if 80 is taken.

Public with a domain

DOMAIN=benchvault.example.com
BENCHVAULT_COOKIE_SECURE=true

Point the domain's DNS at the host; Caddy obtains and renews a certificate automatically. Ports 80 and 443 must be reachable from the internet.

Do not remap HTTP_PORT/HTTPS_PORT in the public case. Automatic certificate issuance needs the host's real ports 80 and 443 published for the ACME challenge.

The two settings must always agree. A Secure cookie over plain HTTP is discarded by the browser, so sign-in appears to do nothing at all — no error, no clue. It is the single most common broken deployment.

Data and persistence

Named volumes survive stop, up, and pull:

Volume Contents
data → /data in api Attachments (experiment_files/, analysis_files/), backups/, logs, and config/ (auto-generated jwt_secret.key, encryption.key)
db-data PostgreSQL storage
caddy-data / caddy-config Certificates and Caddy state

Back up the data volume, not just the database. Losing /data/config without having set an explicit BenchVault_ENCRYPTION_KEY makes previously stored SMTP and AI credentials permanently undecryptable — the database alone will not bring them back.

Backups

Both halves matter: the database holds your records, the data volume holds attachments and encryption keys.

# Database
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  | gzip > benchvault-db-$(date +%F).sql.gz

# Attachments + config keys
docker compose exec -T api tar czf - -C /data . > benchvault-data-$(date +%F).tgz

Automate it with cron (Linux) or Task Scheduler (Windows), and copy the output somewhere else — a backup on the same disk as the original is not a backup.

Scripted backups. scripts/backup.sh is Docker-native: it dumps the database and the data volume through the running containers, writes the status files the Server section reads, and prunes old backups (30-day retention). With --cloud it also uploads both artifacts to the cloud provider configured in the app (Settings → Cloud Backup) — the cron-able equivalent of the in-app "Back up now" button, so backups live off-box even if the server dies.

bash scripts/backup.sh                     # on-box only
bash scripts/backup.sh --cloud             # on-box + upload to the app's cloud provider
# cron (daily 03:00, on-box + cloud):
# 0 3 * * * cd /root/benchvault && bash scripts/backup.sh --cloud >> /var/log/benchvault-backup.log 2>&1

Restoring

bash scripts/restore.sh latest              # newest local backup
bash scripts/restore.sh latest --from-cloud # download from the configured cloud provider
bash scripts/restore.sh BenchVault_Backup_benchvault_20260804_120000.zip --yes

restore.sh stops the api service, takes a safety backup first (unless --skip-pre-restore-backup), restores the database and/or data volume (.zip full backups, .sql.gz/.sql database dumps, .tgz data volumes), then starts the api again (or --keep-api-stopped). It asks for typed confirmation unless --yes.

Practise it before you need it

An untested backup is a guess. scripts/restore-test.sh automates the drill: it restores the newest backup into a throwaway stack on ports 8099/8443, verifies the API comes up healthy with your data, then tears the drill down (keep it with --keep to inspect the restored data in a browser first).

bash scripts/restore-test.sh

Do this when you set backups up, and again whenever you change how they run.

Upgrading

docker compose pull && docker compose up -d

Migrations apply automatically as the new api container boots. Take a backup first anyway — schema changes are the one upgrade you cannot undo by pulling the previous image.

You will usually know an update exists before running that command. The web app checks GitHub for newer releases automatically (every install, no cron or manual setup) and shows a dismissible banner in the top of the app when a newer version is out. The check is cached for a few hours and skipped silently when the server cannot reach GitHub. If the repository is private, set BENCHVAULT_UPDATE_CHECK_TOKEN in .env (a fine-grained PAT with read-only Contents or Metadata access to the repo) — GitHub rejects unauthenticated release lookups for private repositories.

Logs and health

docker compose ps            # all three services and their health
docker compose logs -f api   # application log, follow
docker compose logs db       # database, including startup problems
curl http://localhost/api/status

Both db and api report a health status in docker compose ps. caddy does not — if the site is unreachable but api is healthy, check docker compose logs caddy for certificate errors.

A clean api boot ends with gunicorn workers starting and no traceback. The entrypoint waits for the database, runs scripts/migrate.py (baseline schema plus alembic upgrade head), then starts gunicorn — so every boot converges to head and schema drift cannot accumulate on a supported install.
