BenchVault v5.0.5

Changelog

All notable changes to the BenchVault Application will be documented in this file.

The format is based on Keep a Changelog, and this project adheres to Semantic Versioning.

[Unreleased]

Changed

  • AI assistant provider rework. Providers are now Anthropic, OpenAI, OpenRouter, and a Custom OpenAI-compatible endpoint (user base URL + key). The AI settings form shows only the active provider's key field, and a free-text "custom model id" overrides the default model (any provider endpoint, e.g. deepseek/deepseek-chat on OpenRouter). The assistant chat works with every provider through a shared OpenAI-compatible adapter (OpenRouter now actually reachable), and curated per-provider model lists are seeded into AIModels when the table is empty.
  • Account page removed; password moved to Preferences. The /account page (whose left panel only held a Password link) is gone — changing your password now lives under Preferences. Old /account* URLs redirect to the new settings locations.
  • Settings pages share one visual style. Email and Preferences now have the same green section title as the other settings pages, and card titles across the settings area (App preferences, Email/SMTP, AI provider, Models) use the brand color instead of black.
  • Settings pages are width-capped. Database backup, Server, AI assistant, Email, Preferences, Manage users, and Account render in a centered max-width column instead of stretching edge-to-edge on wide screens; data pages keep full width.

[5.0.5] - 2026-08-04

Changed

  • Settings moved out of Account settings into the account menu. The account page now only holds Password; Preferences, Email, Database backup, Server, AI assistant, and Manage users (renamed from Users) are separate items in the avatar menu, Master-only. "Cloud backup" is renamed "Database backup", "AI" is renamed "AI assistant" (header button included), and the old /account/* URLs redirect to their new locations.
  • App backup timestamps follow the host timezone. The api container defaults to UTC, so "Back up now" / automatic-backup filenames and Server card timestamps appeared hours behind scripts/backup.sh runs (which use the host clock). docker-compose.yml now passes a TZ variable to the api container (default UTC; set e.g. TZ=Europe/Belgrade in .env).
  • scripts/backup.sh --cloud uploads one file per run. The db dump and data-volume archive are packaged into a single benchvault-backup-<timestamp>.zip before upload, so scripted runs appear as one backup file in the cloud (matching the in-app zips) instead of two type-grouped artifacts. On-box, the raw benchvault-db-<ts>.sql.gz / benchvault-data-<ts>.tgz pair is still kept for local restores and retention. scripts/restore.sh detects the wrapper zip by content and restores both halves (database dump, then data volume); the app-format BenchVault_Backup_*.zip path is unchanged.

Fixed

  • scripts/restore.sh / restore-test.sh "latest" selection. The picker sorted by file mtime, so the data-volume .tgz (written after the .sql.gz in the same run) was chosen over the database dump. Selection is now by filename timestamp, preferring the most complete format (.zip > .sql.gz > .tgz).
  • scripts/restore.sh --from-cloud false "backup file not found". The existence check ran on the host, but cloud downloads land inside the api container (/data/backups/cloud_downloads/...); the check now runs in the container.
  • scripts/restore-test.sh drill with a .tgz source. The drill verified restored users, which a data-volume-only backup can never satisfy; verification is now source-aware (users for .zip/.sql.gz, files in /data for .tgz).
  • scripts/restore.sh restore from a cloud download actually restores. The per-format restore steps piped from the host (< "$SOURCE_FILE"), but --from-cloud sources live inside the api container — the restore died with "No such file or directory" before touching anything. All branches (.zip/.sql.gz/.sql/.tgz) now detect an in-container source and run the restore inside the containers. --from-cloud also skips re-downloading when the file is already present in the container.
  • scripts/restore-test.sh records the drill result. The drill passed but never wrote restore_test_status, so the Server section always showed "No restore test recorded". The outcome (success/failed, file, message) is now written to the api container on exit — the Backup card reflects it.

[5.0.4] - 2026-08-04

Changed

  • Automatic backups explained in the UI. The Cloud Backup panel's toggle now says how the scheduler works: the API checks every 15 minutes and backs up when the last backup is older than the interval (24h default, BENCHVAULT_AUTO_BACKUP_INTERVAL_HOURS), with results under Server → Backup & restore.
  • Scripted --cloud backups reset the scheduler clock (backup.sh), so the automatic backup doesn't re-fire right after a manual upload.

[5.0.3] - 2026-08-04

Added

  • Automatic cloud backups. The Cloud Backup panel's "Automatic backups" toggle now actually runs: a scheduler in the API performs a cloud backup when enabled and the last one is older than the interval (BENCHVAULT_AUTO_BACKUP_INTERVAL_HOURS, default 24h). A PostgreSQL advisory lock elects a single leader among gunicorn workers, so only one worker backs up even with WEB_CONCURRENCY > 1.
  • scripts/backup.sh --cloud. The scripted backup can now also upload both artifacts to the cloud provider configured in the app — one cron line gives you daily off-box backups (the in-app "Back up now" equivalent).
  • Update banner: version, commits behind, and what's new. The update notification now reads "Version X.X.X available! (N commits behind)" and shows a short preview of the release notes (with a link to the full notes).

[5.0.2] - 2026-08-04

Changed

  • License: MIT → AGPL-3.0-only. BenchVault is now licensed under the GNU Affero General Public License v3.0 (network copyleft: anyone who modifies and serves the app must share their modifications). Self-hosting an unmodified copy carries no obligations. See LICENSE.
  • Server → Updates card now shows the automatic update check. The card previously displayed the legacy cron-script status, which Docker installs never populate ("Update checks are not configured on this server"). It now uses the built-in check: current/latest version, status badge, release notes link, and a helpful error when GitHub can't be reached (e.g. private repository without BENCHVAULT_UPDATE_CHECK_TOKEN).
  • Docker-native backup tooling. scripts/backup.sh, restore.sh, and restore-test.sh were rewritten for the Compose deployment (they previously targeted the retired systemd layout): backups run through the containers and write the status files the Server section reads; restore supports .zip full backups, .sql.gz/.sql dumps and .tgz data volumes, with --from-cloud downloads, safety backups, and api stop/start around the restore; restore-test.sh is an automated restore drill into a throwaway stack. The api image now ships postgresql-client-16 (matching the postgres:16 server), fixing in-app/cloud backups on Docker ("pg_dump not found"). The superseded scripts/check_updates.sh cron script was removed (the automatic update check replaced it).

[5.0.1] - 2026-08-04

Added

  • Automatic update notifications. Every install now checks GitHub for a newer BenchVault release (cached for 6 hours, silently skipped when the server is offline) and the web app shows a dismissible banner when one exists. No cron, no manual check — updates surface on their own after docker compose pull && docker compose up -d.
  • Private-repository support. BENCHVAULT_UPDATE_CHECK_TOKEN (a fine-grained PAT with read-only Contents or Metadata access) lets the update check authenticate to GitHub when the repository is private; a missing token now explains itself instead of failing silently.

[5.0.0] - 2026-08-03

What's new in 5.0

BenchVault is now a web app: open it in your browser instead of installing a desktop program. The old PyQt6 desktop client and the Flutter mobile app are both gone — everyone, on any device, uses the same React-based interface, talking to the same FastAPI server. Installing (or updating) the whole stack is one command: docker compose up -d.

This release also brings the modules that make BenchVault a complete lab notebook in the browser: - Experiments — reactants and a built-in molarity calculator that works out mass to weigh or volume to pipette for you. - Chemical Inventory — track stock levels, with Excel import/export for bulk updates. - Samples — with nested analyses (e.g. NMR, HPLC runs) attached to each sample. - Templates — save an experiment as a reusable starting point. - Equipment scheduling — book instrument time on a weekly calendar. - Graph — a visual, click-through map of how experiments, samples, and chemicals connect. - Search and Tags — find anything across modules, and organize records with color-coded tags. - AI assistant — a chat drawer that can look up records for you. - Audit Log (Master accounts only) — a full history of who changed what.

Added

  • Web frontend (walking skeleton): New React 18 + TypeScript + Vite + Mantine SPA under frontend/ — login, session bootstrap-on-load, and a read-only Experiments list — served same-origin with the API. Auth uses an in-memory access token plus an httpOnly bv_refresh refresh cookie (BENCHVAULT_COOKIE_SECURE gates the Secure flag so the cookie works over local http). Deployed via deploy/deploy_web.sh. First step toward converging on a single web client and retiring the desktop/Flutter apps.
  • CI for the web frontend: The GitHub Actions workflow now also runs on the web-frontend-w0 branch and adds a frontend job (npm lint + test + build).
  • Web experiments (W1): The web app now does full Experiments CRUD — detail view, create, and edit (core fields + parameters + tags) with optimistic-lock 409 conflict handling (reload-latest-and-notify); attachments (upload/download/delete); and the record-integrity surface (delete → Trash, Restore, and Master-only Purge with sample-reference 409). Reactants render read-only (full reactant + inventory editing arrives with W2).
  • Web inventory (W2a): New Chemical Inventory module at /inventory — searchable item table with low-stock highlighting, add/edit/delete (delete surfaces 403 permission and 409 in-use conflicts distinctly), plus Excel import (auto-detected column mapping + preview) and export, mirroring the desktop inventory window. (frontend/)
  • Web reactant editor (W2b): the experiment detail page now edits reactants inline — pick a chemical from inventory, choose a reactant type (Reactant / Stock Solution / Solvent / Other), and the molarity calculator computes mass to weigh or volume to pipette. Adding/removing a reactant consumes/restores the linked inventory quantity when auto-deduct is enabled (removal prompts to restore or keep consumed), mirroring the desktop reactant workflow. (frontend/)
  • Experiments reactant calc model: Final Volume moved out of the experiment Edit form into the Parameters area as a pinned, optional field; changing it (or editing a reactant's target molarity / stock concentration / volume / mass via the new per-row editor) recalculates the affected reactants and re-syncs the linked inventory, behind a confirmation warning. The reactants table now also shows stock concentration and pipette volume. Adds PUT /reactants/{id}. (api/, frontend/)
  • Web samples (W2c): New Samples module at /samples — searchable list with an analyses-count column, a detail view that hosts nested analyses (create/edit/delete) each with file attachments (upload/download/delete), sample create/edit (name, storage location, parent experiment), and the record-integrity surface (delete → Trash, Restore, Master-only Purge). Adds PUT /samples/{id} (sample edit; owner-or-Master, last-write-wins) and GET /analysis-files/{id} (analysis-file download with path allow-list + nosniff). (api/, frontend/)
  • Web frontend (W3a): Dashboard home page at / — an event calendar (experiments / samples / analyses by date, with a day-detail panel and click-through to experiments/samples), a recent-activity feed, and a Master-only totals strip (experiments / samples / inventory / users / DB size). Read-only; adds @mantine/dates + dayjs. Statistics/usage charts deferred to a later pass.
  • Web frontend (W3b): Dashboard refinements — the event calendar now sits beside its day-detail panel (compact, no wasted whitespace), calendar analyses link to their parent sample (adds sample_id to the /calendar/date analysis events), and a new Inventory alerts panel lists low-stock items (via the existing GET /inventory/alerts) linking to the inventory page. Analyses now require a date on save.
  • Web equipment scheduling (W4): New Equipment module at /equipment — manage lab instruments (add/edit, Master-only delete) and book/cancel time reservations on a weekly per-instrument grid (click an empty slot to reserve; 409 overlaps are rejected with a conflict notice; cancel is owner-or-Master). Reservations also now appear as a 4th event type on the dashboard calendar (month markers + day panel), via a CalendarManager change. Backed by the pre-existing /equipment and /reservations APIs. (api/, frontend/)
  • Web audit + activity logs (W5): New Audit Log page at /audit (Master-only, gated by a reusable MasterRoute guard and a Master-only nav item) over the formal AuditLog trail — server-side filters (user / entity type / action type / date range / limit) plus client-side text search, colored action badges, entity deep-links, and row-expandable details. New all-users Activity Log page at /activity — a full-page view of the cross-module recent-changes feed with a module filter, limit selector, and text search, reached via a "View all →" link on the dashboard's recent-activity panel (no new nav item). Adds GET /audit/action-types (Master-only distinct action types) and raises the /dashboard/recent limit cap from 50 to 500. Both history tables paginate client-side (~50 rows/page). (api/, frontend/)
  • Audit coverage extension: the audit log now records CREATE and UPDATE of experiments, samples, analyses, and equipment (plus reservation creation) with field-level detail — a changed-fields diff (old→new) on UPDATE and a snapshot on CREATE, skipping no-op saves. Fills the analysis/equipment gaps and upgrades the previously generic experiment/sample UPDATE entries. Backend-only (router-level, via a new api/audit_utils.py); the /audit page already renders the new entries. (api/)
  • Web knowledge graph (W6): new Graph page at /graph (replaces the unused Statistics slot) — search any record, see its direct connections (samples, analyses, shared tags, shared reactant chemicals) as a force-directed graph, and click a node to re-center and traverse.   • Categories carry a color, shown as a badge on each analysis and as their own node in the graph: a sample links to its categories, and a category links to the distinct samples it was performed on (by name), so every sample sharing an analysis type is one hop apart.
  • Global search matches category names.

  • Web sample QR codes: print a QR label for any sample (sample detail page → QR label, with a live preview and PDF download in the desktop-matching label sizes), and scan a label with your device camera from the samples list header to jump straight to that sample (manual ID entry as a fallback). Sample IDs are now shown as their own column in the samples list and in the detail header, so a code that reads SAMPLE-<id> is easy to relate back to a record. Frontend-only, over the existing sample API. (frontend/)

(api/, frontend/)
  • Web settings: new Master-only Settings page at /settings — toggle app preferences (inventory module, inventory auto-deduct, recent activity) with save-on-toggle, and configure email/SMTP (server, port, sender, TLS, weekly summary) with a send-test-email button. Master-only in depth: a guarded route, a Master-only nav item, and Master-only endpoints. Frontend-only, over the existing /settings API. (frontend/)
  • Web settings feature gating: the web app now honors the Inventory module and Recent activity switches on the Master-only Settings page. Turning Inventory off hides the Inventory nav item, redirects /inventory to the dashboard, replaces "Add reactant" with a note (existing reactants stay editable), and stops inventory auto-deduction; turning Recent activity off hides the dashboard recent-activity panel and redirects /activity. Both are app-wide (all users) and take effect live when a Master toggles them; an unset or unreadable setting defaults to on. Frontend-only, over the existing /settings API. (frontend/)
  • Web account area + cloud backup: a new Account hub, reached from a top-right avatar menu (Account settings / Log out), gathers your settings in one place — app Preferences and Email (Master-only) plus a new Change password section for everyone — replacing the standalone Settings page (/settings now redirects to the account area). Adds a Master-only Cloud Backup section: pick a provider (Koofr / Nextcloud / pCloud / Box / WebDAV), test the connection, save credentials, run a backup on demand, and browse existing cloud backups. Restore stays a guided operation — the page shows the exact scripts/restore.sh … --from-cloud command to run on the server (and the last-restore status), with no browser-triggered restore or backup download. Saving a provider with a secret field left blank keeps the stored credential, so you can change the backup folder without re-typing passwords. Frontend over the existing /cloud/* and /health APIs, plus one backend change: POST /cloud/config now preserves existing credentials on a blank field for the same provider. (api/, frontend/)
  • Web server & database health: a new Master-only Server section in the Account area (/account/server) shows the health of the deployment at a glance — API and database status, database size, per-table record counts, active connections, oldest/newest experiment, the automatic-backup and last-restore status, and whether a software update is available. Read-only, with a single manual Refresh (no background polling). Frontend-only, over the existing /health, /dashboard/database-health, and /info APIs. (frontend/)

Changed

  • Auth error code: A missing or malformed Authorization header now returns 401 Unauthorized (with a WWW-Authenticate: Bearer challenge) instead of 403 Forbidden, per RFC 7235. 403 remains reserved for authenticated-but-forbidden requests (wrong role / not the owner). Implemented via HTTPBearer(auto_error=False) + an explicit check in verify_token.
  • Analysis date now required server-side: POST /samples/{id}/analyses and PUT /analyses/{id} reject a missing, blank, or whitespace-only analysis_date with 422 (previously it defaulted to an empty string). Since the date columns are free-text, a blank date used to persist and later break date-based reads; validation now enforces a non-empty, trimmed date at the API boundary. The web AnalysisCreatePayload.analysis_date type is correspondingly required. (api/, frontend/)

Fixed

  • Cold-start worker race (Docker): gunicorn imports the app once per worker and DatabaseManager.__init__ runs schema DDL, so with WEB_CONCURRENCY>1 concurrent workers raced the same CREATE DATABASE / CREATE TABLE IF NOT EXISTS statements and Postgres deadlock-killed one worker on every fresh-volume boot ([ERROR] Worker (pid:N) exited with code 1., self-healed via respawn). The ensure-database + schema-init critical section is now serialized with a Postgres advisory lock (pg_advisory_lock on the maintenance database); locked workers wait and then no-op. A concurrent CREATE DATABASE from an un-locked older process is tolerated (DuplicateDatabase). (database/db_manager.py)
  • Docker stack env leak: compose variable interpolation gives real shell variables precedence over .env, so a host with legacy desktop-era POSTGRES_DB / POSTGRES_PASSWORD exported silently built a differently-named database with a different password — the ${POSTGRES_PASSWORD:?} guard passed on the host value and the pg_isready healthcheck passed regardless. The db and api services now inject POSTGRES_* directly from .env via env_file (immune to that precedence), and the db healthcheck uses the container's own $POSTGRES_USER / $POSTGRES_DB. (docker-compose.yml, .env.example, docs/DOCKER_DEPLOY_GUIDE.md)
  • Logout cookie attributes: _clear_refresh_cookie now mirrors _set_refresh_cookie (httponly, secure, samesite="strict") instead of Starlette's delete_cookie defaults (samesite="lax"). Cookie matching is unaffected (same name/path), purely cosmetic consistency. (api/routers/auth.py)

[4.4.0] - 2026-06-17

Engineering Foundation & Server-Side Record Integrity

Infrastructure, developer-experience, and server/API record-integrity changes. No breaking changes; existing clients keep working.

Added

  • Docker / Compose self-hosting: New Dockerfile and docker-compose.yml stand up the API server and PostgreSQL 16 together (POSTGRES_PASSWORD=… docker compose up --build). The API container applies the baseline schema and migrations on startup and exposes a /api/status healthcheck. Built from a PyQt-free server dependency set for a slim image.
  • Continuous Integration (GitHub Actions): A CI workflow runs on every push to main/vps-deployment and on pull requests — ruff lint, byte-compile of the Python tree, bash -n shell-syntax checks, and the full pytest suite against a PostgreSQL 16 service container.
  • Database migrations (Alembic): Adopted Alembic as a forward-migration runner with a no-op baseline revision (0001). All future schema changes are version-tracked revisions applied via scripts/migrate.py (baseline schema + alembic upgrade head). The existing init_database() schema builder is now the frozen baseline authority — no new inline ALTER TABLE blocks.
  • Split dependency sets: requirements-server.txt (API/Docker runtime, no GUI) and requirements-dev.txt (server runtime + pytest/httpx/ruff) alongside the full desktop requirements.txt. Single source of truth for the Docker image and CI.
  • Contributor guide: New CONTRIBUTING.md documents local setup, tests, linting, the Alembic migration workflow, and the Docker stack.
  • Record integrity (server/API): Experiments now use optimistic locking — a concurrent edit to the same experiment returns 409 instead of silently overwriting. Deleting an Experiment or Sample now moves it to a recoverable Trash (soft delete) with Restore; only a Master can permanently Purge. Trash/Restore never change inventory; purging an experiment is blocked while any sample still references it. (Schema via Alembic revision 0002. Desktop/mobile UI to follow.)

Changed

  • Lint gate: Added a conservative ruff configuration (pyproject.toml, pyflakes + core pycodestyle) and cleaned the lint baseline — removed unused imports and dead assignments across the codebase. CI now gates on ruff check.

[4.3.0] - 2026-06-15

Security Hardening, Account Recovery & Logout, and Client Resilience

Added

  • Self-Service Password Reset: POST /api/v1/auth/forgot-password now emails a reset code via the configured SMTP server (previously it stored a token but never sent anything). Returns an honest 503 when the server has no email configured, keeps the anti-enumeration generic response, and throttles reset requests per user.
  • Desktop Forgot Password: New two-step Forgot Password? dialog on the login screen — request a code by email, then submit the code with a new password.
  • Logout & Token Revocation: New POST /api/v1/auth/logout records the access token's JTI in revoked_tokens and invalidates the refresh token + session; verify_token now rejects revoked access tokens immediately instead of trusting them for their full lifetime. Desktop and mobile both call server-side logout (best effort).
  • Mobile Refresh Tokens: The mobile app now stores the rotating refresh token, transparently refreshes on 401, and persists both rotated tokens — sessions survive past the 60-minute access-token lifetime instead of forcing hourly re-login.
  • Server Backup Status: Server Info now shows automatic VPS backup, real restore, and restore-test status reported by the API health endpoint.
  • Server Restore Script: Added guarded scripts/restore.sh for VPS/server administrators to restore local or cloud backups, including full ZIP archives with database and attachment files.
  • Re-installation Detection: VPS provisioning script detects existing .env and reuses domain, email, database name, user, and password without prompting. Suppresses first-time endpoint and bootstrap instructions on reruns.
  • Server Update Checker: Daily cron checks the BenchVault repo for available updates and surfaces a notification in Server -> Server Info when a newer commit is available.

Changed

  • Client Resilience: The desktop ApiClient now retries transient failures with backoff — connection errors are retried for any request (nothing reached the server), while timeouts and 502/503/504 responses are retried for reads (GET) only.
  • SQL-Side Pagination: Experiment and inventory listings now apply limit/offset/search in SQL instead of fetching every row and filtering in Python.
  • VPS Script Names: Renamed VPS provisioning and uninstall scripts to benchvault-4.sh and benchvault-4-uninstall.sh, and updated setup links for the benchvault repository name.
  • Server Info Dialog: Simplified backup and restore status rows to show concise status, date/time, and restored table count without verbose backup filenames.
  • Transcription Documentation: Clarified that the Transcription Pack and Whisper models are installed locally per desktop workstation, not on the VPS/API server.

Removed

  • Agent Harness Files: Removed obsolete root agent guidance files and the old transcribe_helper.py helper source; the transcription pack builder now generates its helper script inline.

Fixed

  • 50-Experiment Truncation: The desktop "all experiments" views silently showed only the first 50 experiments; the API-backed facade now pages through all results.
  • VPS Login Startup: Desktop skips localhost API auto-start when the remembered login server is a VPS/external URL, but starts the local API on demand if the user switches back to localhost.
  • VPS Client API Status: Desktop sessions connected to VPS/external APIs no longer show stale localhost API status in the status bar or Server Info.

Security

  • DB Password Encrypted at Rest: The launcher-saved PostgreSQL password in server_config.json is now encrypted with the per-machine key (legacy plaintext configs migrate automatically on first load). Protects against casual exposure (file browsing, AppData backups, screenshots) — not against same-user malware.
  • Configurable CORS: API CORS origins are configurable via BENCHVAULT_CORS_ORIGINS and restricted on VPS deployments instead of allowing all origins.
  • Upload Validation: File uploads are validated by magic bytes (not just extension), and downloads send X-Content-Type-Options: nosniff.
  • API Docs Gating: Swagger/ReDoc are env-gated (BENCHVAULT_ENABLE_API_DOCS) and disabled on VPS deployments; fixed the dead docs URL printed by the provisioner.
  • nginx Hardening: VPS provisioning adds HSTS, X-Frame-Options, nosniff, and Referrer-Policy headers.
  • systemd Sandboxing: The benchvault-api service runs with ProtectSystem=strict, NoNewPrivileges, PrivateTmp, and scoped ReadWritePaths.
  • Encrypted Backups by Default: VPS provisioning generates a GPG key so default backups are encrypted (with a copy-the-key-off-box warning); the update-check cron now runs as the benchvault user instead of root; the DB password written to .env is validated and quoted.
  • Auth Hygiene: Expired refresh_tokens, user_sessions, password_reset_tokens, login_attempts, and revoked_tokens rows are pruned on successful login; removed the hardcoded test DB password fallback (tests now require POSTGRES_PASSWORD).

[4.1.1] - 2026-06-09

[2.4.0] - 2025-12-10

Major Architectural Change - System PostgreSQL Installation

This release represents a strategic shift from bundled portable PostgreSQL to system PostgreSQL installation. This change dramatically improves reliability and reduces installation complexity.

Fixed

PostgreSQL Service Detection and Port Auto-Detection (Hotfix #1 - Final)

  • Issue: Setup wizard reports "PostgreSQL service not running" on fresh PC, or fails to create database when PostgreSQL runs on non-default port
  • Root cause:
  • Initial fix only checked specific hardcoded service names (postgresql-x64-12 through postgresql-x64-16)
  • Fresh PC may have PostgreSQL 17, 32-bit version, or different naming pattern
  • Critical: Fresh PC runs PostgreSQL on port 5433 (not 5432) when 5432 is occupied on network
  • Database creation/check commands default to port 5432 and fail silently
  • Solution: Implemented comprehensive detection with port auto-discovery
  • Service Detection (3-tier):
    • Method 1: Query ALL Windows services for any containing "postgresql" that is RUNNING
    • Method 2: Check specific service names (PostgreSQL 12-17, x64/x86)
    • Method 3: Socket check with 2-second timeout
  • Port Auto-Detection (NEW):
    • Added detect_postgres_port() method that checks ports 5432, 5433, 5434, 5435
    • Updated database_exists() and create_database() to accept and use detected port
    • All psql commands now use -p PORT parameter
  • Impact: Setup wizard now works reliably regardless of PostgreSQL version, architecture, or port configuration

API Server Startup Error Handling (Hotfix #2)

  • Issue: API server crashes with exit code 1, but error message doesn't show the actual error
  • Root cause: Database connection errors not caught in api_server.py, no stderr capture in main.py
  • Solution:
  • Added try-except block around DatabaseManager initialization in api_server.py
  • Added detailed error logging showing database config (with password status, not value)
  • Capture stdout/stderr from API server subprocess
  • Display full error output in error dialog
  • Show if API_DB_PASSWORD is SET or NOT SET (without exposing value)
  • Impact: API server connection errors now provide clear diagnostic information

API Server Unicode Encoding Error (Hotfix #3)

  • Issue: API server crashes immediately with UnicodeEncodeError: 'charmap' codec can't encode character
  • Root cause: Emoji and Unicode characters (📡, ✓, ✗, ⚠, 🧪, 📁, 📊, 👤, 🏠) in print statements cannot be encoded by Windows cp1252 codec when running as subprocess
  • Solution: Replaced all Unicode characters with ASCII text markers in all print statements:
  • api_server.py: 📡 → [API], ✓ → [OK], ❌ → [ERROR]
  • database/db_manager.py: ✓ → [OK], ⚠ → [WARN]
  • main.py: ✓ → [OK], ⚠ → [WARN], 🧪 → [BenchVault], 📁 → [Project], etc.
  • Impact: API server and database initialization now work successfully on Windows without encoding errors

Changed

Database Creation Removed from Setup Wizard (Design Improvement)

  • Issue: Setup wizard hardcoded database name to 'lab_notebook', conflicting with BenchVault's multi-project flexibility
  • Problem: Users/organizations may want custom database names (e.g., "CompanyX_Research", "Chemistry_Lab")
  • Solution: Removed database creation from launcher entirely
  • Launcher now only verifies PostgreSQL installation and service status
  • Main application's existing ProjectSelectorDialog handles all database/project creation
  • Users can choose any database name they want through the project creation interface
  • Impact: Maximum flexibility, no hardcoded names, cleaner separation of concerns
  • User Experience: 1. Launcher: Verifies PostgreSQL → "Setup complete! Click Launch" 2. Main app: Shows Project Selector → "Create New Project" 3. User: Enters project name, database name, description 4. System: Creates database through project system
  • Benefits:
  • No hardcoded database names
  • Consistent with BenchVault's multi-project architecture
  • Launcher is simpler and more focused
  • Full flexibility for naming first and subsequent databases

PostgreSQL Password Change Tools Removed (Simplification)

  • Rationale: Users set their own PostgreSQL password during PostgreSQL installation
  • Changes:
  • Removed security reminder widget from launcher UI
  • Removed change_postgres_password.py and change_password.bat from installer bundle
  • No longer suggesting users change default 'postgres' password (they set their own during install)
  • Impact: Cleaner launcher UI, smaller installer, no unnecessary password reset utilities
  • Note: Users manage PostgreSQL passwords through standard PostgreSQL tools (pgAdmin, psql)

  • Removed portable PostgreSQL bundling from installer
  • Installer size reduced from ~300MB to ~50MB (6x smaller!)
  • Users now install PostgreSQL separately from https://www.postgresql.org/download/

Migration Guide from v1.0 to v2.0

Prerequisites

  • PostgreSQL 12+ installed
  • Environment variables configured
  • Backup of v1.0 SQLite database

Migration Steps

  1. Backup your SQLite database (critical!) bash cp lab_notebook.db lab_notebook_backup.db

  2. Install PostgreSQL (see INSTALLATION_GUIDE.md)

  3. Create new PostgreSQL database sql CREATE DATABASE lab_notebook;

  4. Set environment variables batch setx POSTGRES_HOST "localhost" setx POSTGRES_PORT "5432" setx POSTGRES_DB "lab_notebook" setx POSTGRES_USER "postgres" setx POSTGRES_PASSWORD "your_password"

  5. Run migration script bash python migrate_to_postgresql.py

  6. Verify migration - Login to application - Check experiments, inventory, samples - Verify data integrity

  7. Set up additional users - Login as Master (first registered user) - Add user accounts for lab members - Configure equipment and settings
